## 1. Бізнес-проблема

Роман Крепич, мешканець Тернополя, щомісяця подає показники 4 лічильників (гаряча вода, холодна вода, електроенергія, газ) через сайт **eps.org.ua** — єдиної квитанції тернополян. Процес сьогоді:

1. Відкриває eps.org.ua, входить у особистий кабінет (логін/пароль).
2. Обирає адресу, переходить у вкладку «Показники».
3. Для кожного з 4 лічильників: йде до лічильника фізично, зчитує цифри, повертається до пристрою, вводить значення вручну.
4. Натискає «Передати показники».
5. Повторює щомісяця, дедлайни різні для кожної послуги (електро — до 3-го, газ — до 5-го, вода — до 31-го).

**Біль:**
- Ручне введення цифр 4 рази на місяць — висока ймовірність помилки (переставлена цифра, зайвий нуль).
- Дедлайни різні для кожної послуги — легко забути.
- Немає єдиного місця для перегляду історії витрати та прогнозу рахунку.
- Сайт eps.org.ua не має публічного API — інтеграція можтлива лише через WebView + JS-ін'єкцію.

## 4. Scope boundaries

### In scope (MVP)

1. **OCR-подача показників:** Фото лічильника → розпізнавання цифр → підтвердження → авто-подача на eps.org.ua через WebView.
2. **Нагадування:** Локальні push-нагадування про дедлайни подачі (за 3 дні, за 1 день, у день дедлайну).
3. **Історія витрати:** Графік витрати по місяцях для кожного лічильника, тренд vs попередній місяць.
4. **Прогноз рахунку:** Розрахунок очікуваного рахунку на основі останньої витрати × тариф.
5. **Smart insights:** Аномалії витрати (±15% vs попередній місяць), карбон-футпринт, поради з економії.
6. **Налаштування:** Профіль користувача, EPS-аккаунт, тарифи, налаштування нагадувань.
7. **Android-додаток:** Capacitor-обгортка навколо Next.js веб-додатка.
8. **БД:** Neon PostgreSQL для зберігання показників, тарифів, налаштувань.

### Out of scope (MVP)

- Публічна реєстрація інших користувачів.
- Multi-tenant архітектура.
- Оплата комуналки через додаток (власник використовує е-Тернопіль або iPay.ua).
- Інтеграція з іншими містами.
- Опублікування в Google Play Store.
- Push-сповіщення через сервер (тільки локальні scheduled notifications).
- OCR для нецифрових лічильників (зі стрілочним механізмом).
- Dark mode (DESIGN_SYSTEM.md явно виключає).
- Річна аналітика (потребує 6+ місяців даних — уже є placeholder в історії).

## 5. Ключові обмеження

| Обмеження | Опис | Джерело |
|-----------|------|---------|
| eps.org.ua не має публічного API | Подача показників можлива лише через WebView + JS-ін'єкцію в сторінку eps.org.ua | Дослідження веб-сайту |
| OCR має працювати локально | Фото не повинне завантажуватися на сервер для розпізнавання — конфіденційність | Вимога власника (settings page) |
| Один користувач | Не передбачає аутентифікації багатьох користувачів | Персональний додаток |
| Tailwind CSS 4 + Next.js 16 | Існуючий стек, не міняти | package.json |
| Capacitor для Android | Нативна обгортка для доступу до камери та scheduled notifications | План проєкту |
| Material Design 3 на Android | Компоненти мають відповідати MD3 при рендері в Capacitor | DESIGN_SYSTEM.md §7 |

## 9. Ризики

| Ризик | Ймовірність | Вплив | Мітігування |
|-------|-------------|-------|------------|
| eps.org.ua змінює структуру сторінки → JS-ін'єкція ламається | Висока | Блокує подачу | Моніторинг + fallback до ручного вводу в WebView |
| OCR не розпізнє певні моделі лічильників | Середня | Ручне редагування | Завжди показуємо розпізнане значення для підтвердження |
| Capacitor plugin для ML Kit OCR не існує / нестабільний | Середня | Блокує OCR | Дослідження плагінів (open question OQ-3) |
| Neon free tier обмеження | Низька | БД недоступна | Моніторинг connection limits; 1 користувач = мінімальне навантаження |

## 10. Припущення

1. Власник має обліковий запис на eps.org.ua з логіном/паролем.
2. Структура сторінки eps.org.ua для подачі показників стабільна між сесіями.
3. Лічильники власника — цифрові (не стрілочні), з читабельним дисплеєм.
4. Тарифи не змінюються частіше разу на рік.
5. Власник використовує Android-пристрій (не iOS).
